# Internationalization (i18n)

The web app is localized with [react-i18next]. It ships English plus 8 target locales —
Japanese (`ja`), Simplified Chinese (`zh-CN`), Spanish (`es`), French (`fr`), German (`de`),
Brazilian Portuguese (`pt-BR`), Russian (`ru`), Korean (`ko`).

## Principles

- **English is the single source of truth, authored inline** as
  `t('<ns>:<key>', 'English default')`. The English catalogs under `public/locales/en/` are
  **generated artifacts** — never hand-edited.
- **Catalogs are lazy-loaded per namespace** from `public/locales/<lng>/<ns>.json` via
  `i18next-http-backend`, so only the active locale is fetched and none are bundled into the
  JS.
- **Semantic keys** (`t('menu:file.new', 'New')`), not natural-language keys — so rewording
  English doesn't orphan translations, and context-dependent duplicate words get distinct
  keys. Keys passed to `t()` must be **string literals** (the extractor can't see dynamic
  keys); for labels chosen from data, use a small render-site helper with a `switch` of
  literal `t()` calls.

## Namespaces

`common`, `menu`, `panels`, `dialogs`, `tools`, `toasts`, `errors` are **parser-managed**
(extracted from inline `t()` defaults). `cpVocab` is **generated** from the crease-pattern
tool data module (`src/i18n/cpVocab.ts`, kept in sync by `cpVocab.gen.test.ts`).

Note a surface can span namespaces: the **menu bar's capability-backed action labels**
(New/Open/Save, most Edit/CP/Design actions) render from `common:capability.*` (via
`workspaceCapabilities` and `MenuBar.tsx`), not `menu`.

## Tooling (`scripts/i18n/`, run from `apps/web`)

- **`npm run i18n:extract`** — regenerates the English catalogs from inline defaults
  (`i18next-parser`), regenerates the `cpVocab` English catalog from the data module, and
  seeds every locale's key skeleton. Preserves existing translations; idempotent.
- **`npm run i18n:stamp`** — records the English-source hash for each translated key (used to
  detect staleness when English changes).
- **`npm run i18n:check`** — the CI gate. Fails on: English catalog out of date with source,
  a missing/empty target translation, a stale translation (English changed since it was
  stamped), or an uncovered Rust error code. It is CLDR-plural-aware (single-category locales
  don't need `_one`) and no-network.

## Adding or changing a user-facing string

1. Write `t('<ns>:<key>', 'English default')` in the component.
2. `npm run i18n:extract` → fills `en/<ns>.json`, adds empty slots to the 8 locales.
3. Translate the new/changed keys in each `public/locales/<lng>/<ns>.json`, then
   `npm run i18n:stamp`.
4. `npm run i18n:check` must pass (CI enforces it).

Reword English → the old translation is kept but flagged **stale** by the check until
re-translated + re-stamped.

## Conventions

- **Verbatim in all locales:** brand names (Ori Studio, TreeMaker), file formats (CP, FOLD,
  ORI, ORH, .bps, SVG, PNG, TreeMaker 4/5), acronyms/proper nouns (CAMV, LBL, Maekawa,
  Voronoi). TreeMaker/origami jargon uses each language's native domain terms.
- **Interpolation:** `t('key', '{{count}} items', { count })`; never concatenate translated
  fragments. Preserve every `{{placeholder}}` and `<Trans>` child tag (`<2>…</2>`) identically
  across locales. Count-driven plurals use i18next CLDR forms — each locale's file carries its
  own plural key set.

## Runtime notes

- `src/i18n/index.ts` sets **`returnEmptyString: false`** so any untranslated (empty) key
  falls back to its inline English default rather than rendering blank.
- The language picker lives in Settings → Appearance (`store/localeStore.ts`); the choice is
  persisted to `localStorage` (`treemaker-web-locale`) and sets `<html lang>`.
- Tests initialize i18n via `src/test/setup.ts` so `t()` returns English defaults.
