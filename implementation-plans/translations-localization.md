# Translations / Localization

Add internationalization (i18n) to the Ori Studio web app, with a source-of-truth
architecture where **English lives inline in the source**, all catalogs are generated
artifacts, and CI enforces that no PR can add a user-facing string without its
translations. Translations are LLM-generated **by the coding agent, one surface at a
time**, so each string is translated with full context.

Delivered as **one PR**, implemented in verifiable phases.

## Decisions (locked)

- **Locales:** English base + 8 targets — Japanese (`ja`), Simplified Chinese (`zh-CN`),
  Spanish (`es`), French (`fr`), German (`de`), Brazilian Portuguese (`pt-BR`),
  Russian (`ru`), Korean (`ko`). All LTR (no RTL work).
- **Key style (Approach A):** semantic dotted keys + inline English default —
  `t('menu.file.new', 'New')`. Stable keys mean rewording English marks the 8 translations
  stale (caught by the check) rather than silently orphaning them, and context-dependent
  duplicate words ("Line", "Scale", "Point") get distinct keys/translations. Chosen over
  natural-language keys (`t('New')`) for exactly this drift-safety and disambiguation.
- **Translation authoring:** the coding agent fills each locale **per surface**, after the
  infra is done, working down a checklist one component/screen at a time, asking Zach
  clarifying questions about any ambiguous string before translating. No automated
  translate script.
- **Scope:** web app (`apps/web`) only. The Tauri native menu is being rewritten in JS
  separately — do **not** scope it in. The cp-detect inspector app is out of scope.
- **Enforcement:** CI parity/staleness gate (`i18n:check`, no network) fails any PR with a
  missing or stale translation.

## Background / findings

- **Oriedita has no translations to reuse.** Neither the vendored copy
  (`third_party/oriedita/`) nor upstream ships locale-suffixed resource files; no Weblate,
  no translations repo. We reuse only its ~770 English domain strings as a **glossary** to
  keep origami terminology consistent (Angle Bisector, Rabbit Ear, Flat Foldable Line,
  Voronoi, Mountain/Valley…). MIT-licensed.
- **Our app is greenfield i18n:** React 19 + Vite 7 + TS + zustand, no i18n lib. A few
  hundred UI strings. `menus/menuDefinition.ts` (~103 labels) is well-centralized; the rest
  are inline in ~24 panels + modals. Toasts are centralized in
  `components/GlobalToasts.tsx`.
- **Persistence template:** `store/themeStore.ts` (localStorage `treemaker-web-theme`).
- **Language picker home:** Settings → Appearance (`components/SettingsModal.tsx`).
- **CI:** `.github/workflows/ci.yml` → `web-client` job (`lint:web`/`typecheck:web`/
  `test:web`). The i18n check slots in here. CI has no LLM access → check is parity-only.

## Architecture

**Library:** `react-i18next` + `i18next` + `i18next-http-backend` (lazy locale loading) +
`i18next-browser-languagedetector`. Extraction via `i18next-parser`.

**Keys:** semantic dotted, namespaced by surface — `common`, `menu`, `panels`, `dialogs`,
`tools`, `toasts`, `errors`.

**Layout:**
```
apps/web/public/locales/
  en/{common,menu,panels,dialogs,tools,toasts,errors}.json  # generated by i18n:extract (SoT = inline defaults)
  ja/… zh-CN/… es/… fr/… de/… pt-BR/… ru/… ko/…             # authored by the agent, per surface
  .hashes.json                                               # per-locale per-key hash of English source (staleness)
apps/web/src/i18n/
  index.ts            # i18next init (backend, detector, fallbackLng: 'en', namespaces)
  locales.ts          # SUPPORTED_LOCALES: [{code, englishName, nativeName}]
  glossary.ts         # domain-term EN glossary from Oriedita (reference for the agent)
scripts/i18n/
  extract.mjs         # wraps i18next-parser: rebuild en/*.json; seed empty keys in target locales
  check.mjs           # CI gate: en/*.json matches source + every locale key present, current-hash, non-empty
i18next-parser.config.js
docs/i18n.md          # contributor guide
```

**npm scripts (`apps/web`, surfaced at root):**
- `i18n:extract` — regenerate `en/*.json` from inline defaults; add missing keys to target
  locales as empty; update `.hashes.json` baseline for English.
- `i18n:check` — CI gate (no network): parser check-only + report every missing / stale /
  empty target-locale key. Prints a per-surface gap list the agent uses as its worklist.

There is intentionally **no `i18n:translate` script** — filling is the agent's job so it has
component context. `i18n:check` is what tells the agent (and CI) exactly which keys are
missing or stale.

**Sync guarantees:**
- English can't desync — it's extracted from inline defaults.
- Reword English → its hash changes → the 8 translations for that key go **stale** →
  `i18n:check` fails until re-translated. No hand-tracking.
- Add a new string → key missing in 8 locales → `i18n:check` fails until filled.
- CLAUDE.md rule directs future agents to run `i18n:extract`, then fill gaps reported by
  `i18n:check` for any string-touching PR.

## WASM / Rust string sync (Open Question 4, resolved plan)

All UI strings today are JS-authored (confirmed by heuristic; re-verified in Phase 2c). For
any user-facing text that *originates* in a crate (validation/error messages), the rule is:

- Crates return a **stable error code / enum variant** across the WASM boundary, never
  English prose.
- JS maps code → `t('errors.<code>', 'English fallback')`.
- To prevent drift **without hand-maintenance**: the crate exposes its user-facing codes as
  a list (a `#[test]` or small bin dumps them to `apps/web/src/generated/error-codes.json`,
  same pattern as existing generated artifacts). `i18n:check` asserts every code in that
  file has a matching `errors.<code>` key. Adding a code in Rust without a catalog entry
  fails CI.
- If Phase 2c finds zero such strings (likely), the registry starts empty and the check
  guards the future at no cost now.

## Phases (single PR; each independently verifiable)

### Phase 0 — Infra & tooling (no user-visible change)
- Add deps; `src/i18n/index.ts`, `locales.ts`, `i18next-parser.config.js`.
- Init i18next in `main.tsx` (Suspense, `fallbackLng: 'en'`, EN preloaded, others lazy).
- Add `i18n:extract` + `i18n:check` scripts; seed empty `en/*.json` namespaces + empty
  target-locale dirs.
- **Verify (tooling):** app boots unchanged; a hand-added `t('common.ok','OK')` renders;
  `i18n:extract` writes it to `en/common.json`; `typecheck:web` passes.

### Phase 1 — Language picker & persistence
- `store/localeStore.ts` (mirror `themeStore`; key `treemaker-web-locale`; default via
  detector → `navigator.language`, fallback `en`).
- Language `<Select>` (native names) in Settings → Appearance; wire `changeLanguage`;
  update `<html lang>`.
- **Verify (browser — Zach):** switching persists across reload; `<html lang>` updates.

### Phase 2 — Extraction sweep (English only, no translations yet)
Convert inline strings to `t()` with inline English defaults, surface by surface, so the
English catalog is complete before any translating. Run `i18n:extract` after each.
- **2a — Centralized:** `menuDefinition.ts`, `MenuBar.tsx`, `CommandDialogModal.tsx`,
  Settings tab titles.
- **2b — Modals & screens:** `SettingsModal`, `HelpModal`, `StartScreen`,
  `CpDetectImportModal`, `SelectByIndexModal`, `GlobalToasts` (toasts + `errors`).
- **2c — Panels (~23):** BpEditorPanel, BpPackingPanel, BpTreePanel, ConditionsPanel,
  CpContextToolPanel, CpToolRail, CpViewControlsPanel, CreasePatternPanel,
  DesignMethodChooser, DesignPanel, DiagnosticsPanel, InspectorPanel, NextDocumentAction,
  PanelComponents, SequencePanel, SimulatorPanel, SimulatorSegmentsPanel, ViewportToolbar.
  While here, confirm whether any string comes from a crate (WASM plan above).
- **Verify per sub-phase:** surface renders from the English catalog; `typecheck:web` +
  `test:web` pass; `i18n:extract` idempotent.

### Phase 3 — Translate, surface by surface (agent-authored, checklist-driven)
For each surface in the checklist below, in order: the agent reads the component to
understand each string's meaning, **asks Zach clarifying questions** about anything
ambiguous, then fills all 8 locales for that surface's keys (glossary-consistent), and Zach
verifies the rendered screen in-language before checking it off. `i18n:check` shows the
remaining gaps at any time.
